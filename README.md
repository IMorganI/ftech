# ftech — платёжный оркестратор для лицензированного гемблинга

ftech — единая платёжная прослойка между сайтами казино и платёжными провайдерами. Сайт подключается по
одному API, а ftech сам выбирает, через какой мерчант-аккаунт провести депозит: по валюте, стране игрока,
сумме, дневным и месячным лимитам, комиссии и весам. Если аккаунт отказал или его лимит заполнен — платёж
уходит на следующий. Выплаты игрокам идут возвратом на карты депозитов, остаток выплачивает оператор вручную.

**Модель работы.** Мерчант-аккаунты у провайдеров принадлежат операторам (владельцам лицензий). ftech не
держит деньги игроков: он маршрутизирует платежи, ведёт учёт, сверку и контроль, а зарабатывает комиссию
платформы с успешных депозитов. Номера карт к ftech не попадают — игрок платит на странице провайдера.

## Что умеет

**Депозиты**
- Единый API для всех сайтов: `POST /v1/deposits`, ответ со ссылкой на страницу оплаты провайдера.
- Маршрутизация по валюте, стране, сумме, лимитам (дневной, месячный, порог переключения), приоритету,
  комиссии; режимы «по порядку» и «по весам» (60/30/10); резервный уровень аккаунтов.
- Каскад: провайдер отказал — платёж уходит на следующий аккаунт (до заданного числа попыток).
- «Липкость»: повторный депозит игрока идёт на тот же аккаунт, если он подходит.
- Лимиты заполнены — отказ `capacity_exhausted` с суммой, которую можно принять сейчас.
- Идемпотентность: повтор запроса с тем же ключом не создаёт второй платёж.

**Выплаты**
- Closed loop: сначала возвраты на карты депозитов игрока, остаток — ручная выплата оператора.
- `withdrawalId`: один вывод казино — одна выплата, даже при повторах и параллельных запросах.
- Лимит одной выплаты; крупные ручные выплаты — одобряет один сотрудник, выполняет другой.

**Ответственная игра**
- Самоисключение, дневной лимит депозитов, KYC хранятся у ftech и не перезаписываются депозитом.
- Повышение лимита — только через API и после периода охлаждения (по умолчанию 24 ч).
- Неизменяемый журнал изменений ограничений игрока.

**Провайдеры**
- Viva Wallet (Smart Checkout) — боевая интеграция: оплата, статус, возвраты, проверка суммы и валюты.
- TestPay — учебный провайдер с кабинетом, подписью вебхуков, выпиской и спорами: весь сценарий без договора.
- Новый провайдер — один файл с адаптером и «карточкой»; экран подключения в борде строится сам.

**Контроль денег**
- Сверка с провайдером: статус платежа перепроверяется у провайдера, вебхукам на слово не верим.
- Зачисление только при подтверждённых провайдером сумме и валюте.
- Потерянный ответ провайдера не приводит к двойной оплате: без каскада, пока не выяснится, создан ли платёж.
- Сверка по выписке провайдера (CSV): оплаты, возвраты, чарджбэки, комиссии — с расхождениями.
- Чарджбэки: учёт спора, сроки ответа, проводки, вебхуки сайту.
- Двойная запись (ledger) по каждой операции; проводки неизменяемы.

**Борда (админка)**
- Обзор, аналитика с разбивкой и выгрузкой в CSV, платежи с полной историей каждого и «что дальше».
- «Зависшие деньги»: где и сколько денег ждёт, как давно и что делать.
- Подключение аккаунтов в 4 шага (ключи → проверка → вебхук → запуск), журнал входящих вебхуков.
- Лимиты и ёмкость: сколько ещё можно принять сегодня и когда закончатся лимиты.
- Ручные выплаты, проблемы, чарджбэки, сверка, журнал действий, команда и роли.
- Уведомления в Telegram о том, что требует внимания.

## Быстрый старт в GitHub Codespaces

[![Открыть в GitHub Codespaces](https://github.com/codespaces/badge.svg)](https://codespaces.new/IMorganI/ftech)

1. Нажми кнопку → **Create codespace**. Первый запуск занимает 3–5 минут: поднимаются сервер и база,
   применяются миграции, создаются демо-данные и первый администратор.
2. Откроется файл **DEMO-CREDENTIALS.md** — адрес борды, временный пароль и API-ключ демо-сайта.
3. Открой борду: вкладка **Ports** → порт 3000 → значок глобуса (адрес без `/admin` тоже ведёт в борду).
   При первом входе отсканируй QR-код в приложении-аутентификаторе (Google Authenticator, 1Password, Authy)
   и смени пароль.
4. Раздел **Тест-платёж**: вставь API-ключ, создай депозит, открой страницу оплаты и нажми «Оплатить».

**Каждый следующий запуск** — одна команда в терминале Codespace:

```bash
npm run up
```

Она обновит код, применит миграции, перезапустит сервер и напечатает адрес борды.
После обновления открой борду с очисткой кэша (Cmd+Shift+R / Ctrl+Shift+R).

| Видишь | Что делать |
|---|---|
| HTTP 401 | Порт приватный: Ports → порт 3000 → правый клик → Port Visibility → Public |
| HTTP 502 | Сервер не запущен: `npm run up` |
| HTTP 404 с пустой страницей | Туннель GitHub потерял Codespace: создай новый Codespace |
| Старая версия борды | `npm run up`, затем обнови страницу с очисткой кэша |

Codespace засыпает через 30 минут без активности, данные сохраняются. Адрес Codespace меняется,
поэтому для вебхуков реальных провайдеров нужен туннель или постоянный сервер (`WEBHOOK_BASE_URL`).

## Запуск локально

Нужны Node.js 20+ и Docker.

```bash
cp .env.example .env
# в .env задай ENCRYPTION_KEY:  openssl rand -base64 32
docker compose up -d          # PostgreSQL 16
npm install
npm run migrate               # таблицы
npm run seed                  # демо-оператор, сайт и аккаунты; печатает API-ключ сайта и секрет вебхуков
npm run admin:create -- you@company.com admin
npm run dev                   # http://localhost:3000/admin
```

Проверка: `GET /health` — процесс жив, `GET /ready` — есть связь с базой.

Депозит из командной строки (ключ — из `npm run seed`):

```bash
curl -X POST localhost:3000/v1/deposits \
  -H "Authorization: Bearer ftk_..." -H "Idempotency-Key: demo-0001" \
  -H "Content-Type: application/json" \
  -d '{"amount":2500,"currency":"EUR","player":{"id":"u42","country":"MT","kyc":"verified"}}'
```

В ответе — `paymentUrl`: страница тестового провайдера с кнопками «Оплатить» и «Отклонить».

## Первые шаги в борде

1. **Операторы и аккаунты** → оператор → «Подключить платёжный аккаунт» → выбери провайдера (для пробы — TestPay).
   Пройди 4 шага: ключи → проверка → вебхук (адрес готов сразу, статус обновляется сам) → включить.
2. Там же — **«Подключить сайт»**: API-ключ и секрет подписи вебхуков показываются один раз, передай их
   разработчикам казино.
3. **Тест-платёж**: проведи депозит; в **Платежах** нажми на него — увидишь всю историю.
4. Сделай выплату больше депозитов — появится **ручная выплата**; отметь её с номером перевода.
5. В кабинете TestPay (`/testpay`) оспорь оплату и скачай выписку → **Сверка с провайдером** → загрузи файл.
6. **Лимиты и маршрутизация**: поставь маленький лимит, переведи аккаунт в резерв, включи режим «по весам».
7. **Зависшие деньги** — то, что требует внимания; **Журнал действий** — кто что менял.

Роли сотрудников: **наблюдатель** (только просмотр), **оператор** (оперативные действия: лимиты, выплаты,
проблемы, чарджбэки, сверка), **администратор** (всё, включая ключи, сайты, команду и журнал).

## Как это устроено

```
Сайт казино ──POST /v1/deposits──► Роутер: проверки игрока, выбор аккаунта, резерв лимита (коммит)
                                      │
                                      ▼  запрос к провайдеру — вне транзакции базы
                                 Провайдер ──► paymentUrl ──► игрок платит на странице провайдера
                                      │
                                      ▼  вебхук провайдера: токен адреса + подпись + перепроверка статуса
                                 Успех: резерв → оборот, проводки, событие в очередь
                                 Отказ: резерв снят, каскад на следующий аккаунт, новая ссылка
                                      │
                                      ▼  фоновая доставка: подписанный вебхук сайту, повторы с паузой
                                 Сайт казино
```

Один процесс Node.js (Fastify) и PostgreSQL. Фоновые задачи (`WORKERS_ENABLED=true`):

| Задача | Как часто | Что делает |
|---|---|---|
| Доставка вебхуков сайтам | 1 с | Подписанные уведомления, до 12 попыток с растущей паузой |
| Сверка платежей | 20 с | Нет вебхука дольше `RECONCILE_AFTER_SEC` — спрашивает статус у провайдера сам |
| Необработанные вебхуки | 15 с | Дообрабатывает события, которые не удалось обработать сразу |
| Выплаты | 30 с | Отправляет возвраты, которые не ушли (перезапуск, провайдер недоступен) |
| Уведомления | 30 с | Telegram: проблемы, чарджбэки, лимиты, зависшие платежи |
| Очистка | 1 ч | Журнал входящих вебхуков старше 30 дней |

## Как выбирается аккаунт

1. **Проверки игрока** — самоисключение, лицензия страны оператора, KYC, дневной лимит игрока.
   Не прошёл — отказ. Лимит игрока никогда не обходится через другой аккаунт.
2. **Подходящие аккаунты** — валюта, страна игрока, сумма в диапазоне аккаунта и хватает лимита
   (дневного и месячного, до порога переключения, по умолчанию 95%).
3. **Основные**, резервные — только если ни один основной не подходит.
4. **Прошлый аккаунт игрока**, если он подходит.
5. **Приоритет**, затем режим оператора: «по порядку» — дешевле комиссия, следующий после заполнения;
   «по весам» — дневной оборот выравнивается к долям.
6. **Резерв** суммы в лимите. Успех — резерв становится оборотом и пишутся проводки; отказ — резерв
   снимается, каскад. Лимиты не подходят нигде — `capacity_exhausted` и «максимум сейчас».

Причина выбора записывается в каждую попытку и видна в истории платежа.

## Принципы работы с деньгами

- **Суммы — целые числа в минорных единицах** (центы, `BIGINT`), никаких дробных чисел.
- **Лимиты резервируются под блокировкой** строк в базе: параллельные платежи не переполнят аккаунт.
- **Запрос к провайдеру — вне транзакции базы**: блокировки не держатся секундами.
- **Неизвестность — не отказ.** Ответ провайдера потерян — без каскада, пока провайдер не подтвердит,
  что платежа нет, или не истечёт срок оплаты заказа. «Запрос не отправлен» (нет ключей, нет токена) —
  каскад сразу.
- **Зачисляем только подтверждённое**: статус, сумма и валюта фактической оплаты от провайдера.
- **Вебхуки — inbox**: событие считается обработанным только после успешной обработки; повтор безопасен.
- **Двойная запись**: каждая операция — проводки, сумма которых равна нулю; изменение и удаление
  проводок запрещены на уровне базы.
- **Возвраты не повторяются вслепую**: нет ответа провайдера — проверяет человек, чтобы не вернуть дважды.
- **Оспоренная часть депозита** не возвращается игроку выплатой.
- **Ограничения игрока** хранятся у ftech; из депозита их можно только ужесточить.

## Безопасность

- Ключи провайдеров вводятся в борде и хранятся в базе зашифрованными (AES-256-GCM, `ENCRYPTION_KEY`);
  после сохранения видны только последние 4 символа. В журнал пишется только, какие поля менялись.
- API-ключи сайтов хранятся как хэш, показываются один раз.
- Вебхуки сайтам подписаны HMAC-SHA256 с меткой времени.
- Вебхуки провайдеров: секретный токен в адресе, подпись провайдера (если есть), перепроверка статуса;
  ограничение частоты с одного IP.
- Борда: пароль + 2FA (TOTP), сессии в HttpOnly-cookie с SameSite=Strict, блокировка после неверных попыток,
  изменяющие запросы — только JSON (защита от CSRF), строгая CSP без внешних скриптов, данные выводятся
  только как текст.
- Роли и журнал действий (только добавление); ручная выплата от порога — два разных сотрудника.
- Логи без ключей и токенов; выгрузки CSV защищены от формул в ячейках.
- Учебные провайдеры (мок, TestPay) запрещены при `NODE_ENV=production`.
- `main` защищён: только через pull request с зелёным CI и одобрением владельца (CODEOWNERS).
  Зависимости зафиксированы, установочные скрипты пакетов отключены, `npm audit` в CI, GitHub Actions
  закреплены по хэшу коммита.

## Настройки (.env)

| Переменная | По умолчанию | Что это |
|---|---|---|
| `DATABASE_URL` | — | Подключение к PostgreSQL |
| `ENCRYPTION_KEY` | — | Ключ шифрования секретов, 32 байта в base64: `openssl rand -base64 32` |
| `PUBLIC_BASE_URL` | `http://localhost:3000` | Внешний адрес сервера (ссылки на оплату, адреса вебхуков) |
| `WEBHOOK_BASE_URL` | = `PUBLIC_BASE_URL` | Другой адрес для вебхуков провайдеров (например, туннель) |
| `PORT`, `HOST` | `3000`, `0.0.0.0` | Где слушает сервер |
| `RATE_LIMIT_PER_MINUTE` | `600` | Запросов в минуту на ключ сайта |
| `TRUST_PROXY` | `false` | За прокси/балансировщиком — брать IP клиента из `X-Forwarded-For` |
| `RECONCILE_AFTER_SEC` | `60` | Через сколько секунд без вебхука спрашивать статус у провайдера |
| `WORKERS_ENABLED` | `true` | Фоновые задачи в этом процессе |
| `MOCK_PROVIDER_ENABLED` | `false` | Учебные провайдеры (мок, TestPay). Только для разработки |
| `PROVIDER_SECRET_<REF>` | — | Ключи провайдера из окружения (старый способ; основной — ввод в борде) |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | — | Уведомления в Telegram (`npm run telegram:setup`) |
| `LOG_LEVEL` | `info` | Подробность логов |

`.env` в репозиторий не попадает. Шаблон — `.env.example`.

## Модель данных

| Таблица | Что хранит |
|---|---|
| `operators` | Владелец лицензии: страны, комиссия платформы, правила выплат, режим распределения |
| `sites` | Сайты оператора (хэш API-ключа, адрес и секрет вебхуков) |
| `providers`, `merchant_accounts` | Провайдеры и мерчант-аккаунты: валюта, страны, суммы, лимиты, уровень, вес, ключи (зашифрованы) |
| `account_usage` | Оборот аккаунта по дням и валютам (блокируется при резерве) |
| `players`, `player_restriction_events` | Игрок сайта, его ограничения и журнал их изменений |
| `transactions`, `transaction_attempts` | Депозиты и выплаты; каждая попытка через конкретный аккаунт |
| `payout_legs` | Части выплаты: возвраты на карты и ручные выплаты |
| `ledger_entries` | Проводки (двойная запись, только добавление) |
| `provider_webhook_events`, `provider_webhook_log` | Входящие события провайдеров (inbox) и журнал всех попыток |
| `webhook_deliveries` | Очередь вебхуков сайтам |
| `reconciliation_issues` | Расхождения для ручной проверки |
| `chargebacks`, `chargeback_events` | Споры и их история |
| `report_imports`, `report_lines`, `report_mappings` | Загруженные выписки провайдеров и результат сверки |
| `admin_users`, `admin_sessions`, `audit_log` | Сотрудники, сессии, журнал действий |

Схема — в `migrations/`, применяется по порядку командой `npm run migrate`.

## Тесты и CI

```bash
npm test
```

Тесты, которым нужна база, запускаются при заданном `TEST_DATABASE_URL`. Покрыто: маршрутизация и лимиты
(включая параллельные платежи), каскад и потерянные ответы провайдера, вебхуки (подписи, повторы, inbox),
выплаты и одобрение двумя сотрудниками, ограничения игрока, Viva (на имитации API), чарджбэки и сверка
по выписке, права ролей, сбои (падение процесса между запросом и записью, гонки, повторы).

GitHub Actions на каждый pull request: установка зависимостей, `npm audit`, проверка типов, все тесты
с PostgreSQL 16, сборка.

## Структура репозитория

| Путь | Что внутри |
|---|---|
| `src/routes/` | API для сайтов: депозиты, выплаты, ограничения игроков, вебхуки провайдеров |
| `src/routing/` | Роутер: выбор аккаунта, резерв, каскад |
| `src/payments/` | Отправка провайдеру, обработка вебхуков, сверка |
| `src/payouts/` | Выплаты: возвраты на карты и ручные выплаты |
| `src/players/` | Ограничения игрока (ответственная игра) |
| `src/providers/` | Адаптеры провайдеров (Viva, TestPay, мок), ключи |
| `src/chargebacks/`, `src/reports/` | Чарджбэки, разбор и сверка выписок |
| `src/admin/` | API борды: вход, роли, подключения, аналитика, ёмкость, история платежа |
| `src/webhooks/`, `src/notify/` | Вебхуки сайтам, уведомления в Telegram |
| `public/admin/` | Борда (без сборки и внешних зависимостей) |
| `migrations/` | SQL-схема |
| `test/` | Автотесты |
| `docs/` | Документация |
| `.devcontainer/`, `scripts/` | Запуск в Codespaces |
| `prototype/` | Ранний интерактивный прототип логики роутинга |

## Статус и план

Готово: единый API, роутинг с лимитами, весами и резервом, каскад, Viva Wallet, выплаты по closed loop,
ответственная игра, борда с ролями и 2FA, история платежа и зависшие деньги, сверка по выпискам,
чарджбэки, аналитика, уведомления.

Дальше:
1. **Продакшн**: постоянный сервер в ЕС, домен с HTTPS, тестовая и боевая среды, бэкапы базы
   с проверкой восстановления, мониторинг, выкладка по кнопке.
2. **Автотесты борды в браузере** в CI.
3. **Нагрузочный тест** и проверка безопасности перед запуском.
4. **Доступ для операторов-клиентов**: сотрудник оператора видит только своих.
5. **Второй боевой провайдер.**
